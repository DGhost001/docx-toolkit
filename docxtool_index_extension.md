# docx-toolkit: Dynamic Index support (`field-add` / `index-add`)

**Status:** Design proposal for the docx-toolkit maintainers
**Scope:** A *tested-by-implementation* feature gap we hit and solved out-of-band;
this document describes the exact mechanism so it can be integrated into the
toolkit behind proper CLI/API surface.

---

## 0. Summary

The toolkit currently has no way to insert **Word fields** (OOXML `w:fldChar` /
`w:instrText`). One practical consequence: users cannot build the **dynamic
autogenerated index** that Word supports natively — a single `INDEX` field whose
page numbers are recomputed on field update (**F9**), instead of a static list of
paragraphs with hard-coded page numbers.

This proposal adds two small, orthogonal capabilities:

1. `field-add` — insert an arbitrary Word field code at a paragraph (the
   building block, generally useful for `TOC`, `REF`, `PAGEREF`, `XE`, ...).
2. `index-add` (plus the hidden `XE` entry fields it depends on) — assemble a
   dynamic index the way Word does: a real `INDEX` field over a set of hidden
   `XE` index-entry fields placed inline in body paragraphs.

The mechanism below was validated end-to-end with `python-docx` + `lxml` on a
real Word document (round-trips through Word, `F9` reproduces the page list
correctly). The document is self-contained; no project/domain data is required
and nothing in it is project-specific.

---

## 1. Background: how Word's dynamic index works

An autogenerated Word index is *two* things stored in the document:

### 1a. The hidden `XE` (index entry) fields — *marks in the body*

Each `XE` field is placed inline inside a body paragraph near where the indexed
term is discussed. Word uses the **page on which the `XE` field currently sits**
as the page reference. OOXML for a plain entry:

```xml
<w:r><w:fldChar w:fldCharType="begin"/></w:r>
<w:r><w:instrText xml:space="preserve"> XE "foo"  </w:instrText></w:r>
<w:r><w:fldChar w:fldCharType="end"/></w:r>
```

Three entry forms are used in practice:

| Purpose | Field instruction | Rendered in index |
|---|---|---|
| Main/top-level entry | `XE "foo"` | `foo .......... 12, 27` |
| Sub-entry (nested under a main term) | `XE "bar:foo"` (colon) | `foo .......... 12, 27` indented under `bar` |
| Cross-reference ("see") | `XE "foo" \t "See bar"` | `foo .......... See bar` (no page) |
| Range (counting-mode) | `XE "foo" \r "bookmark"` | `foo .......... 12–15` (bookmarked span) |

`XE` fields are hidden by Word (invisible print layouts); they become visible in
"show/hide field codes" and "show all formatting marks" modes only.

### 1b. The `INDEX` field — *the generated list*

Where the reader sees the alphabetical list there is a single `INDEX` field. Its
instruction carries display switches; the *rendered result* is cached between
`separate` and `end`. A representative instruction (English index, dot-leader
tab separator, sub-entries collapsed to level 2, locale 1033):

```xml
<w:instrText xml:space="preserve"> INDEX \e "\t" \c "2" \z "1033" </w:instrText>
```

Crucially, the cached result is **not** one paragraph — the `INDEX` field spans a
**sequence of sibling `<w:p>` elements**:

1. **field-open** paragraph: runs `begin` + `instrText` + `separate`
2. **one cache paragraph per rendered entry** (styles `index 1`, `index 2`,
   `index 3`, each with the dot-leader right tab)
3. **field-close** paragraph: run with `end` fldChar

```
<w:p> begin  <w:instrText> INDEX \e "\t" \c "2" \z "1033" </w:instrText>  separate </w:p>   (open)
<w:p .../>  <w:pStyle w:val="index 1"/>  foo <tab/> 12, 27 </w:p>                              (cache)
<w:p .../>  <w:pStyle w:val="index 2"/>  sub <tab/> 12 </w:p>                                  (cache)
<w:p> end </w:p>                                                                             (close)
```

On update (**F9**, or right-click → Update Field), Word discards the cached
paragraphs between `separate` and `end` and regenerates them from the `XE`
positions — recomputing page numbers and re-sorting/re-merging entries.

> **Why this matters for the toolkit:** the index page numbers no longer go
> stale after later edits. Adding/removing body content, inserting figures, or
> re-flowing text all keep the index correct after the next field update. A
> static index (toolkit's current `para-add` of `index 1` paragraphs) cannot do
> this.

## 2. Reference OOXML

Namespaces: `w = http://schemas.openxmlformats.org/wordprocessingml/2006/main`.
`w:fldChar` `@w:fldCharType` ∈ `{begin, separate, end, begin-instr, end-instr}`.

### `XE` field (inline, inside an existing paragraph's run list)

```xml
<w:r><w:fldChar w:fldCharType="begin"/></w:r>
<w:r><w:instrText xml:space="preserve"> XE "foo:bar" \t "See baz" </w:instrText></w:r>
<w:r><w:fldChar w:fldCharType="end"/></w:r>
```

### `INDEX` field (block span)

See §1b. The opening paragraph carries the three runs; the closing paragraph
carries only the `end` run.

## 3. Proposed API

### 3a. CLI commands

Two new subcommands (plus batch op entries), consistent with the existing
conventions (`path` positional, `--after AFTER`, `--container`, `--section`,
`--expect-hash`):

```
docxtool field-add <path> <block_id> --instr CIT --after AFTER?
                                                  [--container C] [--section S]
                                                  [--expect-hash H]

docxtool index-add <path> --after AFTER
                       --xe-pairs "term:page"[,one-per-line]
                       --cross-refs "A:B"[,A:C]
                       [--collapsed 2] [--locale 1033]
                       [--style-main index1] [--style-sub index2]
                       [--container C] [--section S] [--expect-hash H]
```

Plus a hidden-entry helper the toolkit can reuse internally and expose for
power users:

```
docxtool xe-add <path> <block_id> --term "foo:bar" [--see "baz"] [--after AFTER]
                                  [--container C] [--section S] [--expect-hash H]
```

Rationale for the split:
- `field-add` is general (also enables `TOC`, `REF`, `PAGEREF`, `NUMPAGES`, …).
- `xe-add` inserts the hidden mark (this is what puts page references in the
  right place).
- `index-add` builds the `INDEX` field **and**, if given `xe-pairs`, places the
  corresponding `XE` fields in the body and seeds the cached render.

### 3b. `core.py` methods (on `DocxDocument`)

```python
def add_field(self, block_id, instruction, after=None, container="body",
              section=0, mode="inline", expect_hash=None):
    """Insert a field code at a paragraph.
       mode='inline': 3-run begin/instrText/end triplet in the given paragraph.
       mode='index':  build the open+cache+close span (see build_index_field)."""

def add_xe(self, block_id, term, see=None, after=None, container="body",
           section=0, expect_hash=None):
    """Insert a hidden XE index-entry field at paragraph block_id."""

def add_index(self, after, entries=None, collapsed="2", locale="1033",
              main_style="index 1", sub_style="index 2",
              container="body", section=0, expect_hash=None):
    """Build a dynamic INDEX field (open + cached entries + close).
       entries: iterable of (level, term, pageref_or_section) used to seed the
       cached render; if omitted the field is rendered empty until F9."""
```

All return a `{"id": <new_or_block_id>, "hash": ...}` dict like existing ops.

### 3c. Batch mode

Add `field-add`, `xe-add`, `index-add` as ops, so a document can be processed in
one invocation: place a batch of `XE` fields, then `index-add` referencing the
last placed block via the existing `$prev` variable binding.

## 4. Core implementation notes

### 4.1 Field-run helpers

Minimal lxml builder (reuse `OxmlElement`/`qn`):

```python
def _field_runs(instruction):
    r1 = OxmlElement("w:r"); f = OxmlElement("w:fldChar"); f.set(qn("w:fldCharType"), "begin"); r1.append(f)
    r2 = OxmlElement("w:r"); t = OxmlElement("w:instrText"); t.set(qn("xml:space"), "preserve"); t.text = instruction; r2.append(t)
    r3 = OxmlElement("w:r"); f = OxmlElement("w:fldChar"); f.set(qn("w:fldCharType"), "end"); r3.append(f)
    return [r1, r2, r3]
```

For inline insertion, prepend the three runs to the paragraph's existing run
list (insert before `paragraph._p.findall(qn('w:r'))[0]`, i.e. `addprevious`),
so visible text is untouched:

```python
def add_xe(self, block_id, term, see=None, ...):
    instr = ' XE "{}" '.format(_escape(term))
    if see:
        instr = ' XE "{}" \\t "{}" '.format(_escape(term), _escape(see))
    runs = para._p.findall(qn("w:r"))
    if runs:
        for r in reversed(_field_runs(instr)):
            runs[0].addprevious(r)   # rebuild in order
    else:
        for r in _field_runs(instr):
            para._p.append(r)
```

Escaping rules for `instrText`: `"` → `\"`, `\` → `\\`. The tab in the backend
`INDEX` instruction must serialise as a literal backslash-t, i.e. the Python
source uses `" INDEX \\e \"\\t\" \\c \"2\" \\z \"1033\" "`.

### 4.2 `INDEX` span builder

```python
def _index_span(instruction, entries, main_style, sub_style):
    open_p  = _p_with_runs([
        ("fldChar", "begin"), ("text", instruction), ("fldChar", "separate")])
    cache   = [_cache_para(level, term, ref, main_style, sub_style) for (level, term, ref) in entries]
    close_p = _p_with_runs([("fldChar", "end")])
    return [open_p] + cache + [close_p]

def _cache_para(level, term, ref, main_style, sub_style):
    style = main_style if level == 1 else (sub_style if level == 2 else "index 3")
    p = OxmlElement("w:p")
    pPr = OxmlElement("w:pPr")
    ps = OxmlElement("w:pStyle"); ps.set(qn("w:val"), style); pPr.append(ps)
    tabs = OxmlElement("w:tabs")
    tab = OxmlElement("w:tab")
    tab.set(qn("w:val"), "right"); tab.set(qn("w:leader"), "dot"); tab.set(qn("w:pos"), "4448")
    tabs.append(tab); pPr.append(tabs); p.append(pPr)
    r = OxmlElement("w:r")
    for i, part in enumerate([term, ref]):
        if i: r.append(OxmlElement("w:tab"))
        t = OxmlElement("w:t"); t.text = part; t.set(qn("xml:space"), "preserve"); r.append(t)
    p.append(r)
    return p
```

Insert the span after the target block via lxml `addnext` chaining:
`anchor=after_el; for fp in span: anchor.addnext(fp); anchor=fp`.

### 4.3 Styles

`INDEX` caching renders `<w:pStyle w:val="index 1">` etc. If those styles do not
exist in the document's `styles.xml`, add them (paragraph styles, `basedOn`
`Normal`/`Standard`), each with a left indent + hanging indent for the nesting
level (e.g. left 220 hanging 220 for level 1; 440/220 for level 2; 660/220 for
level 3). Prefer importing the document's existing index styles, if present, so
already-styled documents keep their appearance.

## 5. Proposed placement / mapping strategy (the hard part)

To get useful page references automatically you must decide *where* each `XE`
field goes. Precisely replicating a manual author's choices requires semantic
judgment; the toolkit can offer a **best-effort, deterministic heuristic** and
let the user override with explicit `--term`/`--see` anchors. Recommended:

1. **Parse the term list.** Each desired index line is `(level, term, pages-`
   `or-see-target)`. Levels: `1` main, `2`/`3` sub (Word `Parent:Sub` uses the
   parent as the main term).
2. **Build a block → page map** from the document's own Table of Contents
   (`toc 1/2/3` paragraphs carrying `title\t<page>`). Map each body heading to
   its TOC page by *two-pointer* normalised-title matching (both lists are in
   document order; handles duplicate titles like "foo" appearing in several
   chapters). A body paragraph's estimated page is the page of the nearest
   preceding mapped heading. This map is a *target hint only* — Word computes
   the authoritative page on `F9`.
3. **For each term**, score candidate body paragraphs by case-insensitive
   substring hits of the term (plus alias list: strip parentheticals, recognise
   `foo Mode` ↔ `foo`, bare acronyms). Boost section headings (definitional
   locations) over incidental mentions. Skip `toc`/`index`/`Header`/`Footer`
   styled paragraphs and the index section itself.
4. **Choose ≤ N anchors** where `N` = number of distinct target pages, spread
   across distinct estimated pages (one anchor per distinct page). Cross-
   references (`see`) need only **one** anchor anywhere sensible — no page value
   is rendered.
5. Insert an `XE` field at each chosen anchor, then build the `INDEX` field and
   seed its cache from the supplied entry list. The seeded cache makes the index
   readable before the first `F9`; afterwards it is authoritative.

Expose the anchors as a `--dry-run`/`--verbose` listing so a user can inspect
and, if needed, over-ride.

## 6. Edge cases & pitfalls (from the reference implementation)

- **`INDEX` spans multiple `<w:p>`s.** The `end` fldChar MUST be in a final
  sibling paragraph, never nested in the opening paragraph's run list — nesting
  a `<w:p>` inside another `<w:p>` is invalid OOXML.
- **Do not double-resolve `qn` URIs.** `qn("w:fldCharType")` returns the full
  `{…}fldCharType` tag string; set that string directly as the attribute value,
  do not pass it back through `qn()` again (`KeyError` otherwise).
- **Backslash escapes.** The `INDEX \e "…"` separator and `\t` cross-ref switch
  need a serialised backslash. In Python use `"\\t"` (writes `\t`) — writing a
  literal tab into the instruction breaks parsing.
- **Block-id drift.** Block ids are positional and shift after any mutation.
  Place all `XE` fields first, then `index-add`; expose `$prev` chaining in batch
  mode. Re-read / `--expect-hash` between dependent ops.
- **Block enumeration must count paragraphs only.** Iterate `body` children
  filtering to `w:p`; if tables/images/`w:drawing` are counted the paragraph
  index drifts and the block→page map misaligns.
- **Sub-entry colon notation.** To make `F9` nest a sub-entry under its parent
  you MUST place `XE "parent:sub"` (colon), not `XE "sub"`; plain `XE "sub"`
  regenerates a top-level entry.
- **`XE` fields are invisible.** Inserting them must not alter visible text;
  prepend runs to the paragraph's existing run list.
- **Missing index styles.** If `index 1/2/3` styles are absent, Word falls back
  to `Normal` and the dot-leader tab is lost; add the styles (see §4.3).

## 7. Validation strategy

Enhance `validate` to accept and (optionally) report field structure, and add a
focus `verify-index` helper for CI:

1. **OOXML well-formedness** — existing `docxtool validate` must pass with
   `{"valid": true, "errors": [], "warnings": []}`.
2. **Field counts** — inspect `word/document.xml`:
   - exactly one `INDEX` instruction,
   - expected number of `XE "…"` instrTexts,
   - one `index 1/2` style cache block and one `end` close block at the end.
3. **Anchor sanity** — every `XE` field resolves to a real paragraph; the index
   section contains no `XE` fields.
4. **Regression (best-effort)** — if a headless renderer is available
   (LibreOffice), convert to a flat format and assert the index section renders;
   otherwise gate this step behind the renderer's presence.

Older/derivative documents without the `index` styles should continue to
`validate` clean (no new hard errors for pre-existing docs).

## 8. Defaults convention table

| Switch | Meaning | Suggested default |
|---|---|---|
| `\e "\t"` | separator between entry text and page list (dot-leader tab) | `"\t"` |
| `\c "2"` | number of level-2 (sub) columns / collapse depth | `"2"` |
| `\z "1033"` | index sorting locale ID | `"1033"` |
| `..` style id `index 1` | main-entry cache style | `index 1` (create if missing) |
| `$pos=4448` | right dot-leader tab stop (twips) for `index 1` | `4448` |

Localise `\z` per target language; keep `\c` and `\e` as-is for standard English
indexes.

## 9. Suggested CLI examples (placeholder)

```bash
# hide a cross-reference mark next to the paragraph introducing the term
docxtool xe-add manual.docx 152 --term "foo" --see "bar" --after 152

# build the dynamic index after the "Analytical Index" heading (block 900),
# seeding the cache and placing the XE fields
docxtool index-add manual.docx --after 900 \
    --xe-pairs "foo:12,27" "bar sub:13" "baz→see foobar" \
    --cross-refs "quux:see foo"

# generic field for a TOC/REF in one step
docxtool field-add manual.docx 42 --instr ' TOC \o "1-3" \h \z '
```

## 10. Out of scope / future work

- Interactive "pick the definitional page" UI — provide `--dry-run` listing and
  explicit anchor over-rides instead.
- Automatic concordance-file (`\c`) driven index generation from a separately
  supplied term file with heading/mnemonic annotations.
- `XE` `\r "bookmark"` range-reference handling beyond emitting the field code.
- Per-paragraph determine visible-line split for `F9`; this is Word's concern,
  not the toolkit's.

## 11. Acceptance checklist

- [ ] `docxtool field-add` inserts begin/instrText/end for any instruction.
- [ ] `docxtool xe-add` inserts a hidden inline `XE` field; variants
      `parent:sub`, `\t "See …"`, and `\r "bookmark"` all parse.
- [ ] `docxtool index-add` builds the open+cache+close `<w:p>` span after a
      given block; `end` lives in the final sibling paragraph.
- [ ] `index 1/2/3` styles created when absent (basedOn Normal), with correct
      hanging indents and dot-leader right tab.
- [ ] Batch mode supports `field-add`, `xe-add`, `index-add` and `$prev`
      chaining.
- [ ] `docxtool validate` still reports `valid:true` on documents built by
      these commands, and on pre-existing documents without `index` styles.
- [ ] A headless-render smoke test (when the renderer is available) shows the
      index section rendering and `F9` updating page numbers from `XE` fields.
